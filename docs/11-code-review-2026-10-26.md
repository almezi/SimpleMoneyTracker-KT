## Executive summary

This is an unusually well-run codebase for its size. The KMP architecture is real, not cosmetic: one shared UI tree, thin platform hosts, surgical `expect/actual`, bundled SQLite so the platforms cannot drift in SQL behaviour, and comments that consistently explain *why* with references to specs. The money paths are defended properly — atomic import, `insertIfAbsent` for undo, duplicate detection against both the database and the file itself, and an injected clock with zero direct system-clock calls outside `RealClock`.

The findings below are therefore mostly second-order, but several are real. The four that matter most:

1. **Export writes the backup file on the main thread and has no error handling** — the exact failure the import path already guards against.
2. **CSV import does not exist, but both platform pickers accept CSV** — a user round-tripping their own CSV export always lands in the error state, and `README.md` claims CSV import works.
3. **A collector leak in `TambahViewModel`** — every type switch adds another Room flow collector that is never cancelled (`UbahTransaksiViewModel` right next door does this correctly).
4. **Bottom-tab navigation omits `launchSingleTop`/`restoreState`**, which resets tab state (scroll, selected month) on every switch — and *masks* staleness in the pull-based `Ringkasan`/`Anggaran` ViewModels. Fixing the navigation without making those ViewModels reactive will introduce stale-data bugs.

Priority counts: **P1 ×3, P2 ×9, P3 ×8** (plus notes). Everything is actionable in place; nothing requires re-architecture.

## Findings

### P1 — should fix before the next release

#### 1. Backup export: main-thread file I/O and no error handling
`navigation/NavGraph.kt:209-228` launches export in `rememberCoroutineScope()` (main dispatcher). The Android `shareText` then does `File(cacheDir, …).writeText(…)` and `FileProvider.getUriForFile` directly on that dispatcher — `androidMain/.../BackupFileStore.kt:35-52`. For a multi-thousand-transaction JSON export this janks the UI thread and can ANR; and if anything throws (disk full, `FileProvider` misconfiguration), the exception is uncaught inside `rememberCoroutineScope` → **app crash**. The import path wraps everything in `runCatching` (`CadanganViewModel.import`); export got none of that.

Fix (two parts):
- In `AndroidBackupFileStore.shareText`, wrap the file write in `withContext(Dispatchers.IO)` (the UIKit presentation must stay on main — the iOS implementation is fine to present on main, but its `NSFileManager.createFileAtPath` write could also be offloaded).
- In `NavGraph`, wrap each export in `runCatching` and surface a failure toast (`TambahEvent.SaveFailed` is the existing pattern to copy).

Related: `markBackupDone(path)` fires the moment the share sheet is *presented* (`startActivity`/`presentViewController` return immediately), so the status pill turns "Aman" even when the user cancels the share and no file left the device. Consider recording the timestamp only when the user completes a share target, or relabel the status as "export attempted".

#### 2. CSV import is advertised, accepted by the picker, and then always fails
- `CadanganViewModel.import()` (cadangan/CadanganViewModel.kt:84-123) only calls `serializer.parseJson`.
- The Android picker offers `arrayOf("application/json", "text/csv", "*/*")` (androidMain BackupFileStore.kt) and the iOS picker includes `UTTypeCommaSeparatedText` (iosMain BackupFileStore.kt:~95).
- `README.md` says: "Export and import transactions as CSV or JSON."
- `BackupSerializer.parseBackupDate` — the CSV-side date parser — has **no production call site**; it exists only for round-trip tests.

So a user who exports CSV (the "Buka di Excel" row), then imports that exact file, gets the red import-error state every time. Decide one way and make the three layers agree:
- **Cheapest**: restrict both pickers to `application/json` / `UTType.json`, fix the README line, and mark `parseBackupDate` as test-only or delete it.
- **Honest**: implement CSV import — the dedupe key already exists (`duplicateKeyOf`), and categories/accounts would resolve by *name*, which needs a small mapping step the JSON path doesn't have.

#### 3. `TambahViewModel` leaks a Room collector per type switch
`ui/tambah/TambahViewModel.kt:172-176`: `observeCategories(type)` launches a **new** `viewModelScope` collector on every `updateType()` call and never cancels the previous one. After N type toggles there are N concurrent collectors writing the same `_categories` StateFlow. Beyond the unbounded growth, two collectors (old type and new type) can emit out of order and briefly populate the picker with the *wrong type's* categories.

`UbahTransaksiViewModel` already implements the correct pattern three files away (`categoryJob?.cancel()` before relaunching, ui/ubah/UbahTransaksiViewModel.kt:205-213). Copy it — or better, extract it so the two forms cannot drift:

```kotlin
private var categoriesJob: Job? = null
private fun observeCategories(type: TransactionType) {
    categoriesJob?.cancel()
    categoriesJob = viewModelScope.launch {
        repository.getVisibleCategoriesByType(type.storageValue).collect { _categories.value = it }
    }
}
```

#### 4. Tab navigation is missing half of the bottom-nav pattern, and this hides a staleness trap
`SakuApp.kt:73-77`:

```kotlin
navController.navigate(route) { popUpTo(Screen.Tambah) { saveState = true } }
```

The canonical multi-tab pattern needs all three knobs: `launchSingleTop = true`, `popUpTo(start) { saveState = true }`, `restoreState = true`. As written, re-tapping a tab pushes a fresh entry, and saved tab state is never restored — so Daftar's scroll position and **selected month reset on every tab switch**.

There is a second-order effect worth calling out before anyone "fixes" this: the current behaviour *accidentally* keeps `Ringkasan`/`Anggaran` fresh, because those ViewModels are pull-based (`refresh()` on init / screen event only — `RingkasanViewModel.kt:80-107`, `AnggaranViewModel.kt:60-90`) and get recreated on each tab switch. If `restoreState = true` is added, their ViewModelStores survive and the screens will show stale numbers after data changes elsewhere. **Do both together**: fix the navigation flags *and* convert the totals ViewModels to observe the database the way `DaftarViewModel.init` already does (`getAllTransactions().collect { rebuild(...) }`).

While in this area: `DaftarViewModel`'s init collector always rebuilds `currentMonth` (daftar/DaftarViewModel.kt:62-66), so any database write while the user is viewing an older month (e.g. after editing a transaction and returning) snaps the list back to the current month. The collector should rebuild `_uiState.value.month`, not the captured `currentMonth` — and the concurrent `rebuild` launches from `previousMonth/nextMonth/selectMonth` should be funneled through one `Job` so rapid taps can't land out of order.

### P2 — real issues, schedule them

#### 5. Seed failure bricks the app on a loading screen
`data/Seeding.kt:22-32` has no error handling: if any seed insert throws, `onReady` never fires and `SakuApp` shows `SakuLoadingScreen` forever (`SakuApp.kt:44-53` has no timeout or error branch). Same on iOS (`MainViewController.kt:38-55`). Low probability, unrecoverable when hit. Wrap the seed body in `runCatching`, and add an error state (or at minimum a retry) to the loading gate. A loading gate that can hang silently is the worst kind of failure for a local-only app whose data is fine on disk.

#### 6. Cadangan stats are fabricated constants
`ui/cadangan/CadanganScreen.kt:494-496`: `buildStatLine` hard-codes `format(2)` accounts and `format(6)` categories. Users can add categories and the backup file itself carries the real counts — the screen just never reads them. Show the actual counts (they're one query each; `CadanganViewModel` already loads the transaction count), or drop the numbers.

#### 7. CadanganScreen bypasses the design system and the testability machinery
- `CadanganScreen.kt:55-65` defines ten local `Color(0x…)` constants (`ScreenBg`, `CardBg`, `TileBg`, …) that duplicate `SakuColor` tokens — the only screen in the app that does this (grep: `ui/designsystem/SakuColor.kt`, `ui/components/SakuLogo.kt`, `CadanganScreen.kt` are the only files with raw hex). If the palette changes, this screen silently drifts.
- `CadanganScreen.kt:321` uses raw `ModalBottomSheet` instead of the shared `SakuBottomSheet` — which exists precisely to re-arm `automationTestTags()` for out-of-root sheet compositions (see `SakuBottomSheet.kt:44-50` and commit `053a465`). Test tags inside this sheet vanish on Android automation.
- `contentDescription = "Kembali"` (`CadanganScreen.kt:108`) is the one hard-coded UI string in the app, against the repo's own no-literal rule; the sheet's Close button also has no test tag.

#### 8. Inconsistent write-path error handling across ViewModels
`TambahViewModel.save` and `DaftarViewModel.undoDelete` wrap DB writes in `runCatching`; these do not:
- `UbahTransaksiViewModel.save` / `confirmDelete` (ui/ubah/UbahTransaksiViewModel.kt:151-171)
- `AnggaranFormViewModel.save` / `confirmDelete`
- `TambahKategoriViewModel.save`
- `KelolaKategoriViewModel.setHidden/rename/confirmDelete`

An uncaught exception in `viewModelScope` crashes the app. SQLite on a local file rarely fails, but "rarely" is exactly when you want the toast, not a crash. One `runCatching` + event/toast per mutation, matching the Tambah pattern.

#### 9. `TambahKategoriViewModel.save` has no double-tap guard
`ui/kategori/TambahKategoriViewModel.kt:49-72`: unlike `TambahViewModel` (`isSaving` gates `canSave`), the category form's `canSave` is `nameValid && !nameError`. A double-tap launches two save coroutines; the duplicate-name check runs *before* either insert lands, so both pass it. With distinct millisecond timestamps you get two same-name categories; with the same timestamp the second `@Insert` (ABORT) throws an uncaught `SQLiteConstraintException`. Add `isSaving` (and ideally a DB unique index on `(type, customName)` so the rename/create check isn't the only guard).

#### 10. `BudgetRepository.saveBudget` is a read-then-write without a transaction
`data/BudgetRepository.kt:15-27` does `getByCategory` then `upsert` on a plain DAO — two separate DB round trips. Also, `AnggaranFormViewModel.save` (anggaran/AnggaranFormViewModel.kt:75-90) sets `createdAt` itself while `saveBudget` also sets it, so timestamp ownership is split across two layers. Fold the preserve-`createdAt` logic into the repository (or a `useWriterConnection` block) and let the ViewModel pass only user data.

#### 11. iOS import may fail on physical devices: missing security-scoped access
`IosFilePicker.PickerDelegate.documentPicker` (iosMain BackupFileStore.kt:115-122) reads the picked URL with `contentsAtPath` **without** `startAccessingSecurityScopedResource()`. Document-picker URLs are security-scoped; outside the sandbox this typically returns nil on hardware (simulators are lax), which degrades to `""` → JSON parse error → "import failed" with no hint why. Wrap the read:

```kotlin
val granted = url?.startAccessingSecurityScopedResource() == true
val text = path?.let { readUtf8File(it) }
if (granted) url?.stopAccessingSecurityScopedResource()
```

Needs verification on a real device either way (the README's own verification table says no physical device has been attached yet — this is exactly the kind of thing that only fails there).

#### 12. CSV escaping misses newlines
`BackupSerializer.csvEscape` (data/backup/BackupSerializer.kt:~140) quotes on `,` and `"` only. A note containing `\n` breaks the one-row-per-line structure that Excel expects, silently corrupting the export for its stated purpose ("Buka di Excel"). Add `\n`/`\r` to the quote condition.

#### 13. iOS presenter lookup is fragile and failure is silent
`keyViewController()` (iosMain BackupFileStore.kt:~195) takes `.firstOrNull()` of connected scenes and presents from the root VC. If any other VC is already presented, UIKit refuses the presentation; if `keyWindow`/scene lookup fails, `shareText` returns a path, `markBackupDone` records success, and no share sheet ever appeared. Walk `presentedViewController` chains, and treat a nil presenter as an error the caller can show.

### P3 — hygiene, do when convenient

#### 14. Release build hygiene
- `app/build.gradle.kts:19-23`: release disables optimization entirely — no shrinking, no obfuscation. The documented 27 MiB APK is a direct consequence. For an automation-test target this may be deliberate (tags survive R8); if so, record that rationale next to the flag. Note `testTagsAsResourceId` tags do *not* require disabling R8, so "keep automation working" is not by itself a reason.
- `copyReleaseApk` (app/build.gradle.kts:37-45) copies the **debug** APK into `release/` with a version-name file name, while `README.md` documents `assembleRelease` + copying `app-release-unsigned.apk`. Two contradictory release processes; pick one.
- `versionName 2.3`/`versionCode 5` vs README's v2.2 download table (SHA-256 of a file that no longer matches the described build) — the README drift will bite the next person who trusts it.
- Release APK remains unsigned; fine for local use, but it means the published artifact can never be installed without a local signing step — worth one line in the README (it has one; keep it accurate).

#### 15. `:app` module carries stale and unused dependencies
`app/build.gradle.kts` + `gradle/libs.versions.toml`:
- `androidx.appcompat`, `com.google.android.material` — the Material Components library is pulled in solely as the theme parent (`themes.xml` → `Theme.MaterialComponents.DayNight.NoActionBar`). A Compose-only app doesn't need it; `android:Theme.Material.NoActionBar` (or a bare `Theme.SplashScreen`-style parent) drops a whole library.
- `compose.material3`, `material-icons-extended`, `ui-tooling-preview` in `:app` — `MainActivity` uses none of them; all real UI lives in `:composeApp`.
- `composeBom = "2024.02.00"` in `:app` alongside Compose Multiplatform 1.12.1 in `:composeApp` — two Compose toolchains whose artifacts resolve against each other in one APK. Trimming `:app` to `activity-compose` + `lifecycle-viewmodel-compose` (plus whatever the compiler needs transitively) removes the skew entirely.
- Several pins are old by now: `core-ktx 1.10.1`, `activity-compose 1.9.0`, `espresso 3.5.1`, `appcompat 1.6.1`.

#### 16. Dead code
- `Category.displayLabel(defaultResId: Int, fallback: String)` (ui/kategori/TambahKategoriViewModel.kt:81-83): never called, and its `defaultResId` parameter is ignored by its own body. Delete.
- `app/src/androidTest/.../ExampleInstrumentedTest.kt`: template file.
- `BackupSerializer.parseBackupDate`: see finding 2 (delete or implement CSV import).

#### 17. Android Auto Backup ships the database to Google Drive by default
`AndroidManifest.xml` has `allowBackup="true"` and both rule files are still the template TODOs. For an app whose entire pitch is "local-only", the SQLite DB and prefs currently flow into cloud backup with no explicit decision recorded. Either exclude `database/` + `sharedpref/` in both rule files or keep inclusion deliberately with a comment saying so.

#### 18. Hard-coded `Asia/Jakarta` in every date conversion
`SakuFormat.JAKARTA` and `BackupSerializer.JAKARTA` (two constants for one concept — consolidate). Indonesia spans three timezones; WITA/WIT users see dates shifted by an hour off midnight boundaries. The pinning is documented as a deliberate compatibility choice (matching the old SimpleDateFormat behaviour), which is fine — but then it deserves a line in `UI_SPEC.md`, and `formatShortDate(month, day…)`-vs-device-zone should be a conscious product decision, not an accident of history. Also note `SakuFormat.backupDateString`/`parseBackupDate` duplicate the same Jakarta formatting in two classes.

#### 19. Test coverage is good where it is, absent where it hurts
104 tests, and the pure-function core (month totals, dedupe, formatting, budget-row assembly, seed data, backup mapping) is genuinely well tested. The gaps are the classic ones:
- **No ViewModel tests** — finding 3 (the collector leak) is exactly the class of bug `kotlinx-coroutines-test` + a fake repository would catch; the ViewModels are already constructor-injected and clock-injected, so they are testable *now*.
- **No DAO/database tests** — Room KMP supports in-memory DBs on Android host tests; the SQL worth pinning (`expenseTotalsByCategory`, `insertIfAbsent`, `countsByCategory`) currently has no executable specification.
- **No Android-side UI test** — documented reason (no Robolectric for `runComposeUiTest`), and the iOS simulator tree covers the shared tree partially; acceptable, but it means the automation coverage lives outside the repo.

#### 20. Small nits
- `SakuContainer.kt:3` imports a symbol from its own package (`import id.almezi.simplemoneytracker_kt.SakuContainer`) — redundant self-import.
- `AndroidFilePicker.onPicked` is overwritten if `present` is called twice before the first result (edge case; clear-and-null the pending callback defensively).
- `DaftarViewModel.previousMonth` has no lower bound (can walk back to year 1); the month picker has bounds, the arrows don't.
- `UbahTransaksiViewModel.updateType` clears a now-invalid category only when the next flow emission lands (async), where `Tambah` does it synchronously via `switchedTo` — a transient mismatch window; share the synchronous helper.
- `KelolaKategoriViewModel` is pull-based `reload()` after every mutation — correct today because all mutations go through itself, but any future out-of-band write (import) leaves it stale; same class of issue as finding 4.

## What this codebase gets right (keep doing this)

- **Comment discipline.** Nearly every non-obvious decision carries a *why* with a spec pointer (`UI_SPEC.md:16`, `docs/09 §5.5`) or a verified experiment (`build.gradle.kts` header on CMP resource accessors). The `bottomTabFor` doc explaining the `hasRoute` member-vs-extension resolution trap will save someone an hour. This is the best-documented 11k-line codebase I've reviewed.
- **Data integrity on the money paths.** `restoreImport` in one `immediateTransaction`; `deleteCustomCategoryAtomically` moving transactions + deleting the budget + deleting the category atomically; `insertIfAbsent(IGNORE)` so undo-after-add can't crash; import dedupe against the DB *and* within the file itself.
- **Real KMP, not KMP-shaped Android code.** One UI tree, `TRUNCATE` journal mode chosen deliberately (with the WAL bug it fixes referenced), bundled SQLite for cross-platform SQL parity, `Dispatchers.IO` vs `Dispatchers.Default` isolated into a single `buildDatabase` parameter, and the two `BackupFileStore` implementations as honest mirrors.
- **Testability as architecture.** Injectable clock enforced to the letter (zero leaks — verified by grep), test tags as a first-class concern including the `automationTestTags()` re-arm for out-of-root sheets, `switchedTo` extracted from the ViewModel specifically so the type-switch rule is testable without a database.
- **Backward-compatible backup format** — `prettyPrintIndent = " "` and `explicitNulls` kept byte-comparable with pre-migration `org.json` output. Rare to see format compatibility treated this seriously in a hobby-grade app.
